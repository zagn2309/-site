# RAG: доступ LLM к собственным знаниям

## 1. Что такое RAG
RAG (Retrieval-Augmented Generation) — генерация ответа с предварительным поиском релевантных данных. Приложение сначала находит нужные фрагменты документов, затем передает их языковой модели в контексте запроса. Поиск и генерация являются разными задачами.

## 2. Зачем нужен RAG
RAG подходит для внутренних документов: инструкций, регламентов, учебных материалов и баз знаний. Документы можно обновлять без дообучения модели. Найденные фрагменты снижают риск ответа «из головы», а metadata позволяет показать источник.

## 3. Ограничения обычного LLM-запроса
Без RAG модель отвечает на основе своих параметров и переданного контекста. Если данных нет, она может ошибиться или придумать правдоподобный ответ. Передавать весь архив документов в каждый запрос дорого, медленно и ограничено размером контекста.

## 4. Пример
Без RAG студент отвечает только по памяти. С RAG он сначала открывает конспект, находит нужный абзац и формулирует ответ по нему. RAG не заменяет LLM, а подготавливает полезный контекст.

## 5. Полный конвейер
Документы PDF, DOCX, TXT или Markdown преобразуются в chunks, затем в embeddings и сохраняются в vector database. Retriever находит Top-K фрагментов, prompt builder добавляет их в запрос, а LLM формирует ответ.

## 6. Две фазы RAG
Индексация offline: документы очищаются, разбиваются на фрагменты, векторизуются и сохраняются. Обработка запроса online: вопрос векторизуется, выполняется поиск, кандидаты отбираются или rerank-ятся, затем строится prompt и вызывается LLM. Документы не нужно пересчитывать при каждом вопросе.

## 7. Источники и metadata
Источниками могут быть PDF, DOCX, TXT, HTML, Markdown, базы данных и внутренние API. Для каждого фрагмента полезно сохранять имя файла, раздел, страницу, дату и идентификатор документа. Metadata нужна для фильтрации и показа источника.

## 8. Chunking
Большой документ делят на небольшие смысловые фрагменты. Слишком большой chunk содержит лишний текст, слишком маленький теряет контекст. Практический старт: 300–800 токенов с небольшим перекрытием. Лучше делить по абзацам и заголовкам, а не только по числу символов.

## 9. Embeddings
Embedding превращает текст в числовой вектор фиксированной длины. Семантически близкие тексты находятся близко в векторном пространстве. Документы и пользовательские вопросы нужно векторизовать согласованным способом.

## 10. Vector database
Векторное хранилище содержит векторы, исходный текст, идентификатор и metadata. Оно быстро возвращает Top-K похожих фрагментов. Для учебного проекта можно использовать локальный Qdrant.

## 11. Retriever
Retriever получает вопрос и возвращает кандидатов на роль контекста. Базовый вариант — dense vector search по cosine similarity. Для кодов, терминов и точных названий полезен hybrid search: semantic search плюс keyword/BM25. Top-K обычно выбирают в диапазоне 5–10 и подбирают по тестам.

## 12. Reranker
Первый поиск должен быть быстрым и широким. Reranker повторно оценивает небольшой набор кандидатов и оставляет наиболее релевантные. Это дает баланс скорости и точности.

## 13. Prompt builder
Prompt builder объединяет системную инструкцию, вопрос пользователя и найденный контекст. Надежная инструкция: отвечать только по контексту, а при недостатке данных прямо сообщать об этом. Полезно передавать названия источников и разделов.

## 14. LLM в RAG
LLM получает отобранный контекст и формирует ответ. RAG не гарантирует истину: если retrieval нашел неверный фрагмент, генерация тоже может быть неверной. Поэтому качество retrieval и generation оценивают отдельно.

## 15. Обработка одного вопроса
Вопрос -> embedding или поиск -> Top-K -> prompt -> LLM -> ответ. Например, вопрос «Как оформить отчет?» должен привести к разделу «Требования к отчету». Приложение формирует контекст заранее: LLM не ищет самостоятельно по всей базе.

## 16. Минимальная архитектура
User -> API приложения -> поиск -> Top-K chunks -> prompt -> LLM -> answer. Плюсы: мало компонентов, простая отладка и быстрый MVP. Минус: точные термины и неоднозначные запросы могут находиться хуже.

## 17. Hybrid search и rerank
Hybrid pipeline объединяет dense search и keyword search, затем применяет reranker и передает лучшие фрагменты в prompt. Он лучше для точных идентификаторов, но сложнее, медленнее и требует больше ресурсов. Для небольшого корпуса достаточно простого поиска.

## 18. Как обосновывать архитектуру
Решение связывают с требованием, причиной и компромиссом. Например: нужна локальная работа -> локальное векторное хранилище -> не нужен облачный сервис -> усложняется эксплуатация. Сравнивают качество, скорость, стоимость, сложность, приватность и масштабирование.

## 19. Сравнение dense и hybrid
Dense search хорошо находит смысловую близость, проще и быстрее, подходит для MVP и небольшого корпуса. Hybrid плюс rerank лучше для точных терминов и keyword-heavy запросов, но сложнее и медленнее.

## 20. Типичные ошибки
Ошибки: слишком большие или маленькие chunks; отсутствие metadata; слишком маленький Top-K; слишком большой Top-K и шум; только vector search для точных идентификаторов; отсутствие тестовых вопросов и метрик качества.

## 21. Тестирование RAG
Нужно создать 10–20 вопросов с заранее известными правильными источниками. Проверять, попал ли нужный chunk в Top-K, отвечает ли LLM только по найденным данным, измерять latency, число chunks, ошибки и случаи «данных недостаточно».

## 22. Учебный кейс
Есть документы учебной группы: расписание, правила зачета, инструкция по Git и требования к проекту. На вопрос «Сколько баллов нужно для зачета по проекту?» RAG должен найти фрагмент с критериями оценки, передать его LLM и показать источник.

## 23. Практическое задание
Выбрать предметную область и документы, спроектировать pipeline, обосновать компоненты и протестировать систему. Минимальный кодовый прототип может использовать локальный Qdrant и embeddings.

## 24. Результат обучения
После изучения темы студент умеет объяснить RAG, назвать компоненты, различать chunking, embedding, retrieval и generation, объяснить hybrid search и reranking, обосновать архитектуру и предложить план тестирования.
